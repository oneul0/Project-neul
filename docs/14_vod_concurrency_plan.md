# VOD Concurrency And Safety Plan

작성일: 2026-03-31

## 배경

현재 VOD 분석은 다음 구조로 동작한다.

- 사용자 요청은 HTTP로 들어오지만 실제 분석 작업은 백그라운드 비동기로 실행된다.
- VOD 하나 내부에서는 CHZZK 채팅 청크를 순차적으로 요청한다.
- 서로 다른 VOD 분석 작업은 동시에 여러 개 실행될 수 있다.
- 현재는 사용자별 동시 분석 제한이나 시스템 전체 동시 실행 제한이 없다.

즉, 소수 사용자는 문제 없을 수 있지만 동시 요청이 늘어나면 collector, analyzer, Kafka, DB에 부하가 빠르게 쌓일 수 있다.

## 향후 구현 목표

다음 기능은 추후 우선순위로 구현한다.

1. 현재 인프라 기준 안전 동시 처리량 측정
2. 측정 결과 기반 전체 시스템 동시 분석 제한
3. 사용자별 동시 VOD 분석 제한
4. 초과 요청에 대한 대기 또는 거절 정책 정의
5. 상태 UI에 대기중/실행중/제한초과 표시

## 먼저 측정할 항목

동시 분석 제한을 바로 하드코딩하지 말고 아래를 먼저 측정한다.

- VOD 1건당 평균 분석 시간
- VOD 1건당 평균 pagesProcessed, chatsCollected
- collector outbound 요청 지연
- analyzer 메모리 사용량
- Kafka lag 증가 여부
- core-api 저장 지연
- 동시에 1건, 2건, 3건, 5건 실행 시 처리 시간 변화

## 초기 가설

현재 구조를 기준으로 한 보수적인 초기 가설은 아래와 같다.

- 사용자당 동시 VOD 분석: 1건
- 시스템 전체 동시 VOD 분석: 2~3건

이 값은 실제 측정 후 조정한다.

## 구현 방향

### 1. 시스템 전체 제한

- collector에 전역 실행중 작업 수를 둔다.
- 최대 동시 실행 수를 넘으면 새 작업은 바로 실행하지 않는다.
- 정책은 둘 중 하나로 정한다.
  - 즉시 거절
  - 대기열 등록

초기 구현은 단순성과 안정성을 위해 "즉시 거절"이 더 적합하다.

### 2. 사용자별 제한

- 로그인한 owner channel id 기준으로 실행중 작업 수를 관리한다.
- 동일 사용자에 대해서는 동시에 1건만 허용한다.
- 이미 실행중이면 "이미 분석중인 VOD가 있습니다"로 응답한다.

### 3. 상태 모델 확장

현재 상태:

- IDLE
- REQUESTED
- CRAWLING
- ANALYZING
- COMPLETED
- FAILED

추후 추가 후보:

- QUEUED
- REJECTED_LIMIT

## UI 반영 계획

프론트에는 아래가 보여야 한다.

- 현재 실행중인지
- 대기중인지
- 제한 때문에 시작되지 않았는지
- 동일 사용자의 다른 VOD 작업 때문에 막혔는지

예시 문구:

- "현재 다른 다시보기 분석이 진행 중입니다."
- "시스템 분석 슬롯이 가득 차 있어 잠시 후 다시 시도해 주세요."
- "대기열에 등록되었습니다."

## 운영 체크리스트

추후 실제 적용 전 확인할 것:

- 동시 분석 1건 기준 정상 동작
- 동시 분석 2건 기준 정상 동작
- 제한 초과 시 예상한 응답 반환
- 상태가 stuck 되지 않는지
- 실패 작업이 슬롯을 정상 반납하는지
- collector 재시작 후 상태 복구 정책이 필요한지

## 결론

이 항목은 "나중에 구현"이 아니라 "측정 후 제한값 결정"이 핵심이다.

즉 다음 실제 작업 순서는 아래와 같다.

1. 동시 분석 부하 측정
2. 안전 범위 결정
3. 사용자별/시스템별 제한 로직 추가
4. UI와 상태 문구 반영
