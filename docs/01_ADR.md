# Architecture Decision Records (ADR)

이 문서는 "늘(Neul)" 프로젝트의 주요 아키텍처 결정 사항을 기록합니다.

---

## [ADR-001] Direct NID Chat WebSocket Protocol 도입

- **날짜:** 2026-03-14
- **결정 안건:** 치지직 공식 API 대신 내부 WebSocket 프로토콜(NID Chat) 직접 연동
- **배경 및 문제 상황:** 
  - 치지직 공식 API는 일일 호출 제한(10만 건)이 있어 대규모 실시간 채팅 수집에 한계가 있음.
  - 보안 패킷 분석 결과, 브라우저에서 사용하는 내부 웹소켓 프로토콜을 사용하면 제한 없이 실시간 데이터 수집이 가능함을 확인.
- **고려한 대안들:**
  - **대안 1 (공식 API):** 구현이 쉬우나 확장성 부족.
  - **대안 2 (셀레니움/크롤링):** 리소스 소모가 너무 크고 속도가 느림.
- **최종 결정 및 에이전트의 생각:**
  - **결정:** 대안 2 (내부 WebSocket 직접 연동).
  - **이유:** 서버 부하를 최소화하면서 실시간성을 극대화할 수 있음. `NidChatCollector`를 통해 구현 완료.

## [ADR-002] 1-Minute Reactive Micro-batching 도입

- **날짜:** 2026-03-14
- **결정 안건:** 개별 메시지 처리 방식에서 1분 단위 배치 처리 방식으로 전환
- **배경 및 문제 상황:**
  - 초당 수천 건의 채팅이 발생하는 환경에서 Kafka 및 LLM 분석 엔진에 과부하가 발생할 우려가 있음.
  - 유저(스트리머)는 1초 단위의 감정 변화보다 일정 기간(1분)의 통계치를 확인하는 데 더 큰 가치를 느낌.
- **고려한 대안들:**
  - **대안 1 (실시간 처리):** 높은 연산 비용 발생.
  - **대안 2 (윈도우 기반 배치):** 처리 효율성 증대 및 데이터 압축 용이.
- **최종 결정 및 에이전트의 생각:**
  - **결정:** Project Reactor의 `.window(Duration.ofMinutes(1))`를 이용한 마이크로 배칭.
  - **이유:** 인프라 비용 절감 및 향후 Rust 모듈로의 전환 시 데이터 전달 효율성이 높음.

## [ADR-003] DTO 통합 및 `common` 모듈화

- **날짜:** 2026-03-14
- **결정 안건:** 각 모듈에 산재한 DTO를 `common` 모듈로 통합
- **배경 및 문제 상황:**
  - `collector`, `analyzer`, `core-api` 간 데이터 교환 시 중복된 DTO 클래스가 많아 유지보수가 어렵고 필드 불일치 오류가 잦음.
- **고려한 대안들:**
  - **대안 1 (각자 유지):** 독립성은 높으나 중복 코드 증가.
  - **대안 2 (Shared Module):** 상속 및 인터페이스를 통한 타입 안전성 확보.
- **최종 결정 및 에이전트의 생각:**
  - **결정:** `backend/common` 모듈 생성 및 DTO 이동.
  - **이유:** 프로젝트 규모가 커짐에 따라 일관된 데이터 구조 정의가 필수적임.
