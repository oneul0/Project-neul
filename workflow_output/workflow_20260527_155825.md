# Planner 구현 계획서

## 1. 목표 요약

`VodController` (core-api) 와 `VodCollectorController` (collector)가 현재 **Repository 직접 호출, 외부 WebClient 인라인 생성, 도메인 정책 인라인, 트랜잭션·보상 트랜잭션 오케스트레이션, 비동기 구독, 사용자향 에러 메시지 하드코딩** 등 서비스 계층의 책임을 다수 침범하고 있다. 이를 별도 **Application/Domain Service + Gateway 계층**으로 분리해 컨트롤러는 "HTTP 어댑터"(요청 검증 → 서비스 호출 → HTTP 매핑)에만 집중하도록 리팩토링한다. **API 계약(경로/응답 코드/응답 본문)은 완전히 보존**하며, 회귀를 막기 위해 리팩토링 *전에* WebFlux 슬라이스 테스트와 서비스 단위 테스트를 먼저 추가한다.

## 2. 선택된 접근법

### 채택: "Service-First + Gateway 분리" — 점진적 책임 이관 (5단계)

기존 컨트롤러를 한 번에 갈아엎지 않고, **신규 서비스/게이트웨이 클래스를 먼저 도입 → 컨트롤러가 그것을 호출하도록 위임 → 인라인 코드 제거** 순서로 진행한다. 각 단계마다 API 계약/E2E 통과 여부를 검증할 수 있다.

### 대안 비교

| 대안 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| **A. Service-First + Gateway 분리 (채택)** | 단계별 검증 가능, 롤백 쉬움, API 계약 보존 명확 | 중간 단계가 다소 장황, 단계 수 多 | ✅ |
| B. 컨트롤러 전체 한번에 재작성 | 빠름 | 회귀 위험 高, 테스트 없으면 사실상 검증 불가 | ❌ |
| C. 헥사고날 풀 리팩토링(포트/어댑터, DTO 계층, 도메인 모델) | 장기 유지보수성 최상 | 본 작업 범위 초과, 일정/리스크 과다 | ❌ (별도 단계로 분리) |
| D. core-api ↔ collector HTTP 결합을 이벤트(Kafka)로 분리 | 양방향 결합 근본 해소 | 정합성·운영 복잡도 급증, 메시지 스키마 협의 필요 | ❌ (별도 PR로 분리) |

**선택 이유**: 본 작업은 "컨트롤러의 서비스 책임 침범"에 한정된 리팩토링이다. 양방향 HTTP 결합과 R2DBC 트랜잭션 경계는 구조적 부채로 남기되, 게이트웨이 캡슐화만 수행해 다음 단계의 디딤돌을 마련한다.

### ⚠️ 불일치 또는 주의 필요

1. **단계 4 의사코드의 `OwnerIdentityResolver.requireOwnerId(req).flatMap(...)` 표기**
   - 실제: `String resolveOwnerId(ServerWebExchange exchange)` (동기, null 가능)
   - 영향: Plan대로 작성하면 컴파일 실패. ownerId가 `null/blank`일 때의 분기(현재 `syncOwnerLibrary`에서 처리)도 명시 필요.

2. **단계 3/4 서비스 메서드 시그니처 `long videoNo`**
   - 실제: 모든 레퍼지토리/엔티티/컨트롤러가 `String videoNo`. `Long`은 PK용이지 videoNo가 아님.
   - 영향: 그대로 코드화 시 즉시 컴파일 실패.

3. **단계 6 테스트 계획의 "ACQUIRED → 202"**
   - 실제: `ResponseEntity::ok` → 200 (`VodController.java` L119).
   - 영향: 스냅샷 테스트의 expectation이 잘못 작성될 수 있음. 의도가 "현재 200을 202로 정정"이라면 그것도 별도 PR로 분리해야 한다.

4. **`vodHighlightRepository.deleteAllByVideoNo(...)` 반환은 `Mono<Integer>`**
   - Plan에는 결과 사용 여부가 명시되지 않음. Orchestrator에서 `.then()`로 무시할 것임을 명시 권장.

5. **`getTimeline`의 `onErrorResume` 폴백 분기 (L79–87)**
   - Plan은 "빈 결과 시 폴백"만 언급하고 "에러 시 폴백"은 단순히 흡수한다고만 적음.
   - 실제 코드는 **빈 결과 폴백(L70–78)** 과 **에러 시 폴백(L79–87)** 이 **다른 분기**이고, 후자는 폴백 안에 **이중 onErrorResume**(L83–86)으로 빈 Flux를 반환함. 서비스 이전 시 이 의미를 정확히 보존해야 함.

6. **`getHighlights`의 `onErrorResume` 폴백은 `syncOwnerLibrary` 호출을 건너뜀**
   - 정상 경로: 라이브러리 sync 수행 → 정렬된 highlights 반환.
   - 에러 경로(L55–58): 라이브러리 sync **없이** default 정렬만 반환.
   - Plan은 이 비대칭을 언급하지 않음. `VodHighlightQueryService`로 옮길 때 동일하게 비대칭을 보존할 것인지(현 동작 유지) 명확히 결정 필요.

7. **단계 0 슬라이스 테스트의 실행 가능성**
   - 현재 `VodController.collectorWebClient`는 필드 인스턴스화. `@WebFluxTest` 슬라이스에서 외부 HTTP를 가로채려면 `MockWebServer`를 `localhost:8081`에 띄우거나, 먼저 단계 1을 수행해 Bean으로 분리해야 함.
   - 권장: **단계 0의 `triggerAnalysis` 테스트는 단계 1 이후로 미루거나, 단계 0과 단계 1을 함께 묶음**.

- **`syncOwnerLibrary`의 `analyzed=true/false` 분기**: 현재 어떤 테스트에서도 markAnalyzed vs touchVideo 호출 여부를 명시 검증하지 않음.
- **`toFallbackTimelinePoint`의 점수→participantCount/messageCount 휴리스틱**: `VodFlowE2ETest.timeline_fallbackFromHighlights`(L108–122)는 `startSeconds`만 검증, 매핑 수식 검증 안 함.
- **`triggerAnalysis`의 ACQUIRED→200 응답과 외부 HTTP 호출 실패 시 보상 트랜잭션**: 어떤 테스트에서도 검증 안 됨.
- **`VodCollectorController.getStatus`의 30분 경계와 highlight 폴백**: 테스트 부재.
- **`VodCollectorController.triggerCrawl`의 중복 가드와 fire-and-forget 동작**: 테스트 부재.

→ Plan의 단계 0과 신규 단위 테스트가 이 모든 갭을 정확히 겨냥하므로 방향성은 적절. 다만 **시그니처 오류와 단계 0 실행 가능성 문제를 먼저 정정한 뒤** 작성해야 함.

## 결론

**조건부 승인.** Plan의 전체 구조(Service-First + Gateway 분리, 6단계 점진적 이관, 단계별 git 커밋 분리)와 위험 식별/완화 전략은 매우 우수합니다. 컨트롤러 책임 침범 6가지를 정확히 진단했고, 양방향 HTTP 결합·트랜잭션 경계 등 본 PR 범위 외 부채도 명시적으로 분리한 점이 훌륭합니다.

다만 **3개의 사실 오류(시그니처 `long`, `requireOwnerId` 메서드명, "ACQUIRED→202")** 와 **1개의 실행 가능성 문제(단계 0 슬라이스 테스트가 inline WebClient를 가로챌 수 없음)** 가 그대로 구현되면 시작부터 컴파일·테스트 실패를 일으킵니다. 위 "수정 제안 1)~6)"을 적용해 Plan을 미세 정정한 뒤 구현을 진행할 것을 권합니다. 정정 자체는 30분 이내 작업이며, 정정 후에는 단계 진행을 막을 구조적 문제가 없습니다.
